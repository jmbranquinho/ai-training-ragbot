Chatbot
In this module, you will build a chatbot that answers questions from a website using RAG (Retrieval-Augmented Generation). But just as important as getting the chatbot to answer correctly is how you structure the project along the way. AI engineering has more in common with software engineering than with data science and data engineering.

 

Data scientists and data engineers often work exploratory: the code grows in a notebook, one step at a time, while looking for something that works. This often ends up in the same file, logic and configuration are mixed together, dependencies are created where they are needed, and “what works” is left. It is an effective way to explore, but it scales poorly. The result is quickly tightly coupled code that is difficult to test, change, and reuse. Software engineers work the opposite way: they clarify needs, model the domain and choose a structure before coding, separate responsibilities into clear components, and let the code grow in a way that can withstand change. This module introduces that way of working.

This is software development that happens to be about AI, not notebook work with a little cleanup at the end.

Background
A public entity wants to make the information on its website more accessible. Instead of citizens having to navigate through menus and long pages, they want a chatbot that answers questions.

 

Your task is to build a working prototype: fetch content from stavanger.kommune.no , make the content searchable, and connect to a language model that responds based on the fetched content. You are free to choose a website other than stavanger.kommune.no , but remember to check robots.txt before you start. A tip to easily assess whether a website is suitable for fetching content is to open the page in reading mode and see if the necessary information is present.

Distinguish between “what” and “how”
This module is as much about how you build as what you build . A key point is to distinguish two things:

What the solution does - the actual task, described in terms a professional understands: a Document is divided into Chunks , we find the most relevant chunks for a Question , and the model provides an Answer (preferably with a source). This is also where the rules reside, for example “a should preferably point back to the document it came from”.

How it does it - the technical choices: are the chunks in Postgres or Azure AI Search? Which LLM is used to generate responses?

 

The core of an application is often called the domain and deals with the “what.” These are the concepts and rules of your problem, regardless of the surrounding technology.

 

Why bother about the distinction?
Because the how part changes often. YOU might change the database, embedding model, or LLM along the way. If the core logic doesn't know about these choices, you can replace them without having to make major changes to the code.

 

A concrete picture: instead of your code saying “store this in this particular Postgres database”, it says “I need something that can store a chunk and retrieve it”. Exactly what that something is, you decide somewhere else. Then you can start simple, for example store in memory while you develop, and switch to a real database later, without touching the kernel. This contract between the kernel and the outside world is what is called an interface .

 

You don't need to know all the theory behind this to solve the task, but if you want to learn more, you can read up on Domain-Driven Design and/or Ports and Adapters (and possibly other software design principles).

Preserve metadata: URL, title, section, retrieved date
Take into account robots.txt if it exists for the website you are scraping.
